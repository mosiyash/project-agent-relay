# project-agent-relay

Локальный CLI-оркестратор для read-only исследования зарегистрированных проектов AI-агентом. Из любого каталога пользователь указывает логическое имя проекта и вопрос; relay находит проект в явном белом списке, запускает runner в его корне, валидирует структурированный ответ и сохраняет отчёт для аудита.

MVP не содержит MCP, HTTP-сервер, UI, очередь задач или режим редактирования.

## Требования

- Node.js 20 или новее;
- OpenCode CLI для runner `opencode`;
- настроенная авторизация OpenCode в его локальном credential store.

Адаптер проверен с OpenCode `1.19.5`. Используемый batch-интерфейс: `opencode run --pure --format json --agent ... --dir ...`. Relay не передаёт `--auto`.

## Установка

```bash
npm install
npm run build
npm link
```

После `npm link` команда `project-agent-relay` доступна из других проектов на этой машине. Для запуска без link используйте `node /path/to/project-agent-relay/dist/src/cli.js`.

Чтобы агенты OpenCode в любых проектах знали о relay и могли вызывать только его команду исследования, установите global skill:

```bash
project-agent-relay install-opencode-skill
```

Команда создаёт `~/.config/opencode/skills/project-agent-relay/SKILL.md` и добавляет в `~/.config/opencode/opencode.json(c)` узкие `bash`-правила только для lifecycle-команд `project-agent-relay ask|resume|status|latest`. Существующий skill не заменяется без `--force`. Если `opencode.jsonc` содержит комментарии, installer намеренно откажется его перезаписывать; добавьте правила вручную или удалите комментарии перед повторным запуском.

После установки перезапустите OpenCode: global skills и конфигурация загружаются только при старте. В другом проекте можно сказать агенту: «Узнай в CRM, как реализована доставка транзакционных писем». Skill направит его к зарегистрированному проекту через relay, а не к прямому чтению чужого каталога.

## Конфигурация

По умолчанию реестр читается из:

```text
~/.config/project-agent-relay/projects.json
```

Путь можно переопределить переменной `PROJECT_AGENT_RELAY_CONFIG` или опцией `--config`. Это путь к реестру, а не к целевому проекту. Произвольный целевой путь CLI не принимает.

Возьмите структуру из `projects.example.json`:

```json
{
  "version": 1,
  "defaults": {
    "timeoutMs": 900000,
    "idleTimeoutMs": 120000,
    "maxReportBytes": 262144
  },
  "projects": [
    {
      "name": "crm",
      "path": "/home/example/projects/crm",
      "runner": {
        "type": "opencode",
        "executable": "opencode"
      },
      "instructionPaths": ["AGENTS.md", "docs/architecture.md"]
    }
  ]
}
```

Правила реестра:

- `name` содержит строчные латинские буквы, цифры, `_` и `-`;
- `aliases` опционален и содержит уникальные дополнительные имена того же проекта;
- `path` является абсолютным путём к доступному каталогу и не может быть корнем файловой системы;
- `runner.type` сейчас поддерживает `opencode` и тестовый `fake`;
- `instructionPaths` содержит только относительные пути внутри проекта;
- чувствительные имена и пути с `..` в `instructionPaths` отклоняются;
- `timeoutMs` задаёт аварийный hard limit и ограничен диапазоном от 1 секунды до 30 минут;
- `idleTimeoutMs` останавливает runner только при отсутствии событий и ограничен диапазоном от 30 секунд до 10 минут;
- `maxReportBytes` ограничен диапазоном от 1 КиБ до 1 МиБ.

`fake` возвращает детерминированный пустой отчёт и не читает проект. Он предназначен для локальной проверки CLI и тестов, а не для исследования кода.

## Использование

```bash
project-agent-relay ask \
  --follow \
  --profile implementation \
  --project crm \
  --question "Как реализована доставка транзакционных писем?"
```

Успешная команда печатает JSON-отчёт в stdout и путь сохранённой копии в stderr. Отчёт содержит:

`--follow` печатает в stderr компактный heartbeat раз в 30 секунд: текущий model step, время последней активности и накопленные input/output token counters. Начало и готовность отчёта выводятся отдельными строками. `--follow-details` включает диагностический поток с отдельными read/search/tool событиями. Содержимое файлов, текст модели и raw tool output не выводятся ни в одном режиме. При timeout relay завершает process group runner-а, записывает статус `timed_out` и последнее событие в audit log. Отмена уже отправленного запроса на стороне AI-провайдера всё равно зависит от поддержки cancellation самим провайдером.

Global skill запускает Bash tool с внешним timeout `960000ms`, который больше локального hard limit `900000ms`. Relay отдельно применяет inactivity timeout `120000ms`, первым завершает свою process group и возвращает `[TIMEOUT]`. Skill запрещает повторный `ask` после timeout, interruption или пустого результата: сначала проверяется `status`, готовый результат восстанавливается через `latest`, а продолжение той же target-сессии выполняется через `resume`.

Каждый `ask` печатает `Run ID` и сохраняет OpenCode session ID без текста вопроса. Lifecycle-команды позволяют восстановить результат или продолжить ту же target-сессию:

```bash
project-agent-relay status --run <run-id>
project-agent-relay latest --project mssh
project-agent-relay resume --follow --profile answer \
  --run <run-id> \
  --question "Используется ли внешний production-провайдер?"
```

`resume` выбирает профиль заново для каждого уточнения, но передаёт OpenCode сохранённый `sessionID`. Одновременно для одного canonical project разрешён только один active run. Пути файлов в отчёте считаются доказательными ссылками: source-агент не читает их напрямую, а при нехватке деталей задаёт target-агенту follow-up через `resume`.

Если target-модель вернула JSON с неверным синтаксисом или схемой, relay один раз выполняет format-only correction в той же OpenCode session. Repair запрещает новое исследование, ограничен двумя model steps и повторно проходит строгую валидацию. Второй невалидный ответ завершает run ошибкой `REPORT` и не выводится как успешный отчёт.

`--profile` управляет формой и стоимостью исследования, не изменяя исходный вопрос:

- `answer`: конкретный факт, до 8 model steps; target возвращает только `summary` и `unanswered_questions`, без списка файлов и разбора механизма;
- `implementation`: разбор реализации, flow, конфигурации, тестов и рисков, до 20 model steps; это значение по умолчанию для прямого CLI-вызова;
- `transfer`: полный разбор для переноса с разделением переносимых практик и project-specific деталей, до 30 model steps.

Global skill выбирает `answer` для вопросов «какой/что используется/какая версия», `implementation` для «как реализовано/устроено» и `transfer` для «как сделать так же/перенести/предложить для нашего проекта». Сообщение пользователя считается инструкцией source-агенту, а не готовым prompt для target project. Source-агент сохраняет намерение, но формулирует самостоятельный вопрос, на который можно ответить только по target project. Маршрутизация, действия source-агента и контекст «у нас/нам/текущий проект» в relay не передаются; они применяются после получения отчёта.

- `summary`;
- `files` с путём и назначением;
- `flow`;
- `configuration` только с именами и назначением настроек;
- `tests`;
- `transferable_practices`;
- `project_specific_details`;
- `risks`;
- `unanswered_questions`.

## Хранение

По умолчанию данные сохраняются в `${XDG_STATE_HOME:-~/.local/state}/project-agent-relay`:

- `reports/*.json` содержит валидированные отчёты;
- `runs/*.json` содержит lifecycle metadata и OpenCode session ID без текста вопросов;
- `audit.jsonl` содержит время, имя проекта, runner, статус, длительность и код ошибки.

В audit log не записываются вопрос, prompt, ответ модели и значения конфигурации целевого проекта. Каталоги создаются с режимом `0700`, новые файлы с `0600`.

## Модель безопасности

- Целевой проект выбирается только по имени из локального реестра.
- Перед запуском проверяются существование, тип и доступность каталога; runner получает его canonical path.
- Процесс запускается через `spawn(executable, args)` с `shell: false`; prompt передаётся напрямую через stdin и не интерполируется в shell-команду или positional-аргумент.
- OpenCode запускается с `--pure`, поэтому плагины целевого проекта не загружаются.
- Global OpenCode skill получает только разрешения на `project-agent-relay ask|resume|status|latest`; он не получает разрешение на произвольные shell-команды или прямой доступ к другим проектам.
- Inline agent policy сначала запрещает все инструменты, затем разрешает только `read`, `glob` и `grep`; `edit`, shell, subagents, web и внешний доступ остаются запрещёнными.
- Дополнительные deny-правила блокируют `.env`, ключи, токены, секреты и дампы. Единый prompt повторяет эти ограничения и запрещает изменения.
- Дочерний процесс получает очищенное окружение без API-токенов и других произвольных переменных. Поэтому provider должен быть авторизован через credential store OpenCode, а не только через переменную окружения.
- Время выполнения, stdout runner-а и размер итогового отчёта ограничены.
- Relay не содержит операций записи в целевой проект.

Ограничение процесса ОС: CLI запускается от текущего пользователя и не является filesystem sandbox. Гарантии MVP основаны на deny-policy OpenCode, отключении внешних плагинов, отсутствии shell-инструмента и read-only prompt. Для защиты от скомпрометированного бинарника runner-а нужен отдельный OS sandbox, которого в MVP нет.

## Коды завершения

- `0`: успех;
- `1`: внутренняя ошибка;
- `2`: неверные аргументы или конфигурация;
- `3`: проект отсутствует в реестре или недоступен;
- `4`: runner не запустился, завершился с ошибкой, превысил timeout или лимит вывода;
- `5`: ответ runner-а не является допустимым отчётом.

## Разработка

```bash
npm run format:check
npm run lint
npm run typecheck
npm test
```

Тесты не вызывают модель: они проверяют валидацию allowlist-конфигурации, prompt, безопасный массив аргументов и очищенное окружение, обработку ошибки процесса, JSONL OpenCode и схему отчёта.

## Текущие ограничения

- Реализован один production adapter: OpenCode. Интерфейс runner допускает добавление других адаптеров.
- Реальная полнота исследования зависит от модели и от файлов, доступных read-only инструментам.
- Relay не проверяет семантическую истинность отчёта, только его структуру и размер.
- Audit log является локальным append-only по соглашению, но не имеет криптографической защиты от изменения владельцем машины.
